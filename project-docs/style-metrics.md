# Style Metrics

Этот файл нужен для объективной фиксации расхождения между редактурой Codex и финальной редактурой редактора.

Цель: не просто хранить диффы, а видеть, уменьшается ли стилевой зазор от статьи к статье.

## Базовая идея

Для каждой статьи сравниваются:

- версия после редактуры Codex:
  `project-docs/style-diffs/<slug>.codex-version.md`
- финальная версия после редакторской правки:
  `content/blog/<slug>.md`

Из этого сравнения считаются 3 метрики и одна итоговая сводная оценка.

## Когда создаётся эталон

- эталонная версия Codex должна сохраняться сразу после финальной правки Codex и параллельно с записью рабочей статьи в `content/blog/<slug>.md`
- предпочтительный способ сохранения эталона: копирование уже готового файла статьи в `project-docs/style-diffs/<slug>.codex-version.md`
- это нужно, чтобы не тратить токены на повторную генерацию того же текста
- если эталон не создан в этот момент, дальнейшее стилевое сравнение по статье считается пропущенным

## Когда запускать сравнение

- по умолчанию сравнение запускается после того, как редактор внёс свою правку
- обязательная удобная точка запуска: команда редактора `замени дескрипторы на шорткоды`
- если в этот момент статья уже отредактирована редактором и эталонный файл существует, AI обязан параллельно со своей основной задачей:
  - сравнить эталон с текущей статьёй
  - посчитать метрики
  - записать выводы в `editor-style-notes.md`
  - занести строку в журнал ниже
- этот шаг считается частью pipeline и не должен забываться

## Метрики

### 1. Word Change Rate (`WCR`)

Показывает, какая доля слов была изменена редактором.

Формула:

`WCR = ((deleted_words + inserted_words + replaced_words) / total_words_codex) * 100`

Где:

- `deleted_words` ─ слова, удалённые редактором
- `inserted_words` ─ слова, добавленные редактором
- `replaced_words` ─ слова, заменённые редактором
- `total_words_codex` ─ общее число слов в версии Codex

Смысл:

- чем ниже `WCR`, тем ближе текст Codex к финальной редакторской версии

### 2. Paragraph Touch Rate (`PTR`)

Показывает, какая доля абзацев была затронута редактором.

Формула:

`PTR = (touched_paragraphs / total_paragraphs_codex) * 100`

Где:

- `touched_paragraphs` ─ количество абзацев, в которых есть хотя бы одно изменение
- `total_paragraphs_codex` ─ общее число абзацев в версии Codex

Смысл:

- низкий `PTR` значит, что редактор правит локально
- высокий `PTR` значит, что редактор вынужден проходить почти по всей статье

### 3. Full Rewrite Rate (`FRR`)

Показывает, какая доля абзацев была переписана существенно, а не поправлена точечно.

Формула:

`FRR = (heavily_rewritten_paragraphs / total_paragraphs_codex) * 100`

Абзац считается `heavily rewritten`, если в нём изменено примерно `50%` слов и более, либо если смысловой ритм абзаца очевидно перестроен.

Смысл:

- это самая важная метрика для реального стилевого зазора
- можно иметь умеренный `WCR`, но высокий `FRR`, если редактор заново собирает ключевые абзацы

## Итоговая сводная метрика

### Style Gap Score (`SGS`)

Это основная метрика, по которой отслеживается сближение стилей.

Формула:

`SGS = (0.5 * WCR) + (0.3 * PTR) + (0.2 * FRR)`

Почему такие веса:

- `WCR` отражает общий объём правки
- `PTR` показывает ширину вмешательства по статье
- `FRR` показывает глубину переписывания

Именно `SGS` используем как главную численную оценку.

## Интерпретация

- `0-5` ─ расхождение на уровне погрешности
- `5-10` ─ очень близкий стиль, нужна только лёгкая редакторская доводка
- `10-18` ─ заметный, но уже рабочий зазор
- `18-30` ─ статья требует серьёзной стилистической правки
- `30+` ─ стиль Codex пока явно отличается от редакторского

## Тренд во времени

### Rolling Average (`RA5`)

Среднее значение `SGS` по последним 5 статьям.

Формула:

`RA5 = (SGS1 + SGS2 + SGS3 + SGS4 + SGS5) / 5`

Смысл:

- сглаживает разовые отклонения
- показывает, действительно ли стиль сближается, а не просто одна статья случайно получилась лучше

### Drift Delta (`DD`)

Разница между текущим `SGS` и средним `RA5`.

Формула:

`DD = SGS_current - RA5`

Смысл:

- отрицательное значение означает улучшение относительно недавней нормы
- положительное ─ откат назад

## Критерий «различия на уровне погрешности»

Можно считать, что текущий цикл обучения почти исчерпан, если одновременно выполняются условия:

1. последние 5 статей дают `RA5 <= 8`
2. ни у одной из этих 5 статей `SGS` не выше `10`
3. `FRR` у большинства статей в этой пятёрке не выше `5`

Это означает, что редактор в основном не переписывает текст заново, а лишь шлифует его.

## Что делать после достижения погрешности

Когда различия стабильно падают до уровня погрешности:

1. удалить старые файлы из `project-docs/style-diffs/`
2. очистить журнал метрик ниже
3. начать новый цикл накопления

Перед удалением каждого эталона обязательно:

1. сравнить его с финальной редакторской версией
2. обновить `editor-style-notes.md`
3. записать метрики в журнал

Только после этого эталонный файл можно удалять.

Это полезно, если:

- стиль редактора изменился
- изменился тип тем
- нужно проверить, не возник ли новый зазор после периода хорошего совпадения
